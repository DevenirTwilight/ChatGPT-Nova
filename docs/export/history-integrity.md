# 聊天历史采集与完整性校验设计

当前滚动试验基于224dae2真机再次H06反馈修正加载等待：可识别加载指示时暂停缓存/滚动，消失后重核；列表换入给予5秒准备宽限，正文变化不重置。单窗口30秒硬限、整次10分钟、1200步/原消息/字节限制与取消保留；下文5秒/120秒为初始设计值。真实历史完整性未证明，详见 [本批说明](../dom-export-trial.md)。

实现状态更新：用户已要求可安装版本，工作分支1.4.0/code14接入有界滚动缓存试验。实施细节以 [试用说明](../dom-export-trial.md) 为准：当前缓存置于页面临时内存，通过token隔离，完成/失败/取消清理；原生轮询进度、后台处理最终JSON，未实现独立基准导入和部分文件保存。实现不是完整历史证明，下方为设计阶段记录。

本设计针对 `feature/export-conversation` 的1.3.9/code13（实现f2d0cce，审查起点41b24c1）。本轮任务是检查源码、设计校验并验证现有方案的限制；尚未把滚动采集接入APK。

## 证据与结论

用户转述GPT-5.6 sol对其HTML的检查：7条article，3用户/4助手，且多段已知历史缺失。本环境未收到该HTML字节，未独立解析文件，安装版本及会话分支未知；按用户反馈记录为已知覆盖失败，不将私聊内容或列举的消息正文提交仓库。虚拟化/懒加载是可能原因，尚未独立观察用户页面；选择器漏匹配、隐藏状态、分支变化也需排查。

源码已经足以证明当前实现无法保证完整历史：

| 位置 | 当前行为 | 后果 |
| --- | --- | --- |
| `app/src/main/assets/export/dom-trial.js` 的nodes | 一次querySelectorAll author，过滤user/assistant和隐藏节点 | 只采集当时挂载且被识别的消息；并非所有conversation节点 |
| 同文件messages.push | 输出role/html/markdown；ID只用于当前快照重复检查和签名 | 原生端没有跨快照合并所需稳定ID；排序仅继承当时DOM顺序 |
| `ConversationExport.capture()` | capture → render → verifyOnly → chooseFormat | 无历史加载、滚动、多次收集或正文缓存 |
| `verifyOnly`与signature | 对当前author子树复核，变化时报D10 | 能拒绝快照变化；不能发现始终没挂载的历史；滚动后通常会合理地产生不同签名 |
| `start()`提示 | 建议先到顶部再到底部 | 遇虚拟化，回到底部会再次卸载早期消息，无法靠最终单次采集解决 |
| 原生render/HTML/Markdown | 明示“仅当前已加载消息，完整历史未确认” | 边界提示正确；内容不足以用于完整历史目标 |

结论：单快照路线不满足用户的完整历史目标。继续修D09或格式转换不会补出缺失历史。滚动中即时缓存是可验证的下一方案，不保证一定可行；若不能可靠取得全部目标分支文本，换独立数据来源。旧403仍没有修复证据。

## 完整性的范围与状态

导出范围首先固定为“本次选择的会话分支、采集开始时的已完成消息”。不是所有编辑/重新生成分支，也不是整个项目所有会话。ID不能按字符串、时间或首次看见顺序排序；重生成与编辑可能更换分支。同一路由也可能切分支。

文本、附件元数据、附件原文件、图片原文件是四个独立维度，不是可以相互推导的等级：

| 维度 | 可报告状态 | 通过条件 |
| --- | --- | --- |
| 文本历史 | 当前快照 / 多次采集覆盖未确认 / 与指定基准逐条匹配 / 已确认缺失 / 冲突 | ID、角色、目标分支顺序匹配独立基准，且逐条正文/富文本核验；基准来源和范围仍须人工核实 |
| 附件元数据 | 未检查 / 已观察N个 / 与基准匹配 | 不能把仅看见的名称当作会话所有附件；按消息和附件稳定标识核对 |
| 附件原文件 | 未包含 / 部分 / 与基准文件匹配 | 文件实际可打开、字节与基准校验；名称或下载动作不构成证据 |
| 图片原文件 | 未包含 / 部分 / 与基准文件匹配 | 原文件校验；DOM缩略图、占位和alt不算原图片 |

现有版本附件元数据未单独完整核对、附件/图片原文件均未包含。即使确认文本，也不标为“完整会话备份”。没有独立基准时historyCompleteness保持not-proven。

## 采集状态机

`确认范围 → 当前窗口采样 → 向上遍历 → 向下遍历 → 第二次核对 → 完整性结果页 → 用户选择格式`

任何阶段都可取消。取消不自动生成成功文件，可明确选择保存已收集的部分内容。导航、分支或内容冲突转入失败/重新采集。网页滚动属于新增页面状态改变，不能继续笼统称为“只读DOM探针”；数据读取仍不调用私有API、不hook fetch/React、不读Cookie/storage。

1. 原生持有采集会话token、URL、WebView/Activity代次和限额。正文缓存只在应用内存或私有缓存文件，取消/销毁清理；不写Logcat或公开仓库。诊断只记聚合计数、阶段、轮次与冲突种类。
2. 点击开始时确认未生成，识别实际聊天滚动容器。不能默认window/document.scrollingElement；检查可滚动祖先和消息位置，确保操作移动聊天历史。未识别返回H01_SCROLL_CONTAINER，不猜测。记录原滚动位置供尽力恢复，恢复失败只提示，不伪称成功。
3. 每轮先采样当前窗口的稳定ID/角色、净化正文HTML/Markdown、正文摘要、相邻顺序和局部位置，再移动。快照必须自洽，缺ID/重复ID/嵌套author/空正文均不能静默跳过。内容摘要只用于同ID变化检查，不能用正文哈希去重：同文不同消息必须保留。当前试用版ID可缺失但仍导出；新合并模式应停止自动合并并允许明确的部分导出。
4. 向上按约半个可见窗口滚动，保留重叠锚点。移动后分段等待DOM/消息稳定，例如250ms采样、连续3轮稳定且无生成提示、单步最多5秒；超时记未知，不能把超时当顶部。一次采样结束立即把净化正文和ID交给原生缓存，不能只缓存仍会卸载的DOM引用。每轮回传不超过既有8MiB预算，原生后台解析/合并，evaluateJavascript仍在UI线程。
5. 观察滚动容器到顶且多次无法再上移、无新ID，只记录topObserved=true及稳定轮数。scrollTop=0、加载按钮消失、连续无新增是停止条件证据，不是服务器历史结束证明。需同时记录bottomObserved、是否加载超时、是否达到预算。上行后再以重叠窗口下行到最底，防止只覆盖头/尾。
6. 建立ID顺序约束图：每个快照提供先后边；重叠窗口连接图。仅唯一拓扑顺序可用于导出；若出现环、多个候选顺序、不连通窗口，拒绝合并排序并报告H03_ORDER。即便唯一顺序，也不能证明两个相邻已见ID之间没有未见消息；此处只校验一致性，不把DOM相邻当全局连续性证明。
7. 同ID角色或净化正文变化，或窗口关系表明分支改变，报告H04_CHANGED并重启，不能“最后一次覆盖”混合两个分支。第二次上下遍历需逐条比对累计ID、角色、顺序和净化正文摘要。旧单快照outerHTML签名会随控件/布局变化，不能直接拿来比较跨窗口正文；需要独立的正文摘要，保留现有单快照自洽检查。
8. 初始建议整次最多1000消息、200万净化文本字符、64MiB序列化缓存、300滚动步和120秒。所有阈值待目标设备测量，不自动放宽。达到任何限制记H05_LIMIT，停止并显示部分结果；禁止截断后标成功。用户返回/取消、超时、切页、销毁均废弃迟到回调。还需处理SPA A→B→A：代次与当前URL不足，需采集期观察公开DOM/路由变化并失效token；不得读取私有React状态。

## 导出前校验页

只在设备展示首尾简短预览，不将预览放入可复制诊断。界面至少包含：

```text
采集范围：当前选择的会话分支
已收集：N 条（用户X / 助手Y）
最早 / 最新：本地预览
顶部状态：已观察到滚动顶部 / 未确认
底部状态：已观察到滚动底部 / 未确认
扫描：上行、下行、第二次核对是否完成
顺序与正文：一致 / 冲突 / 无法核对
文本完整性：未确认 / 与指定基准逐条匹配 / 已确认缺失
附件元数据：已观察N个，覆盖未确认
附件原文件：未包含（0个）
图片原文件：未包含（0个）
```

不能仅凭到顶显示“完整历史已加载”。无基准但两轮一致时使用“已遍历并收集可见历史，完整性未确认”。任何错误导致部分内容时，明确提供“保存已收集内容（可能缺失）”和“重新采集”，不自动进入完成状态。HTML/Markdown/PDF必须同步写入范围、文本和文件状态，不能界面保守但文件标完整。无新消息的稳定7条也必须维持未确认。

独立基准可来源于用户提供的官方导出或可逐条核实的来源，先确认会话、目标分支、时间与公开ID能对应。不能从DOM并集自己生成所谓独立基准。已有audit只核对ID/角色/顺序，不核正文；扩展应另行核净化内容和实际保存文件。来源自述不能被程序证明，界面保留来源和检查范围。

## 实施与验收顺序

1. 首先做有取消/进度/诊断的滚动缓存试用，沿用现有SAF和打印；将完整性结果接到选择格式之前。生产接入前需完成跨窗口缓存、顺序/正文冲突与SPA失效测试，不写自动下载附件。
2. 合成夹具覆盖稳定7条且缺中间、虚拟窗口持续卸载、相同正文不同ID、缺/重复ID、顺序环/歧义/无重叠、流式/编辑/重生成、错误滚动容器、超时/取消/限额和导航迟到回调。不能只测最后DOM40条。
3. 用户原长会话实测，核对已知遗漏消息是否恢复，再与独立有序基准逐条核文本和目标分支。消息数量/首尾正确仍不够。没有基准只报告观察到的改善。
4. 真实历史仍缺失且无法可靠加载全量、必需正文不在DOM或顺序无法建立时，停止扩展DOM路线，验证官方导出数据导入等可证明范围的数据源；不要默认旧内部API403已可用。

当前结果：源码审查和校验设计完成；单次快照限制已有独立合成复现。完整历史真实验证未完成。可以开始有界滚动缓存试验，尚不能实现或宣称“完整历史导出”已可靠。本设计未生成新APK。
