# 独立完整性与附件边界（设计，尚未实现产品入口）

当前用户要求先解决单向采集耗时。用户报告27条正常用户/助手最终回复对照无大段遗漏，进度消息与原附件仍缺；保留完整性未确认。这是特定导出范围/时刻的正面观察，不能推广成100%备份。

## 消息ID校验

已有工具 [history-coverage](../../tools/feasibility/history-coverage/README.md) 可按外部有序ID/角色基准离线核对。基准须来自独立于本次DOM采集的材料，如用户提供的官方账号数据导出，并明确会话、选定分支、截止时刻、范围（普通用户消息/最终回复或包含工具进度）。不得从本次缓存或滚动并集生成所谓独立基准；只对照条数或首尾也不能校验中间。

数据文件按消息逐条记录稳定ID、角色、顺序；真实ID/路径/正文仅本地保存。先检查来源和选定分支，网页ID与基准节点ID若不一致，需要可审查的一对一映射，不能靠正文相似、序号、删前缀或去重猜测匹配。报告缺失、额外、重复、角色不符与顺序问题，任何异常均不标覆盖通过。用户自述来源可记录，工具不能证明其真实性。

ID/角色全匹配仅支持“目标消息覆盖与独立基准一致”。要标完整文本已验证，还须逐条核对正文及代码/表格等范围；DOM转换Markdown不是原始Markdown，不能把ID相等当正文保真。基准若排除了工具进度，结果必须明确范围。缺少可独立取得的基准时持续标not-proven，不通过增加滚动次数升级状态。本批29场景中，永不挂载m17时可观察两端并成功生成39条，这个限制明确保留。

## 附件方案审查

现有导出器保留有限链接/图片占位，不获取附件原文件；无完整附件清单可用，不可仅按文件名声明附件元数据完整。四维状态分别为主文本、附件元数据、附件原文件、图片原文件。

| 候选方式 | 条件与边界 |
| --- | --- |
| 用户选择本地原文件，导出ZIP | 优先试验方式；用系统文件选择器授权，将文件与消息/附件明确关联，记录字节数与SHA256。HTML保留离线相对路径，ZIP包含清单。仅“用户选入的原文件已包含”，不声称账号全部附件已备份。 |
| 沿网页正常下载入口获取文件 | 后续独立验证；需要用户实际可用下载入口，可能有过期链接。复用既有下载的同源凭据规则，不逆向内部API，不读Cookie/React/storage。不能把下载失败当占位成功。 |
| 仅保留文件名/链接/占位 | 当前文本导出的边界；不属于附件原文件备份，不能升级完整性。 |

未来ZIP需限制文件数/总大小、拒绝路径穿越和名称冲突，保留每项成功/失败状态。没有独立附件清单不能确认“全部原文件”。上述只是设计；本批不接入基准导入、网络附件抓取或ZIP产品功能。
